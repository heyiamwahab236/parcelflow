# Operations guide

These are procedures to use and verify after deployment. They are not records of completed cloud drills.

## Diagnose a failing release

```bash
kubectl get pods,deploy,hpa,pdb,ingress -n parcelflow
kubectl get events -n parcelflow --sort-by=.lastTimestamp
kubectl logs -n parcelflow deployment/api --tail=100
kubectl logs -n parcelflow job/parcelflow-migrate --tail=100
kubectl describe pod -n parcelflow POD_NAME
```

| Symptom                     | Investigate                                                                                                                                    |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| API fails at startup        | Pod Identity agent, role association, KMS permissions, initialized secret versions and regional endpoints.                                     |
| `/readyz` returns 503       | RDS health, database security group, application role/password and verified TLS.                                                               |
| Migration job fails         | Master-secret permissions, DB reachability, migration checksum mismatch or incompatible SQL. New workloads are not applied after this failure. |
| ALB target unhealthy        | Service selector/port, `/readyz`, ALB controller logs and security-group rules.                                                                |
| `ImagePullBackOff`          | ECR repository/digest, node pull permission and outbound network access.                                                                       |
| HPA reports unknown metrics | metrics-server health and CPU resource requests.                                                                                               |
| `409` on scan update        | Another operator updated the shipment, or the transition is invalid. Refresh and review.                                                       |
| CI vulnerability gate fails | Read the affected package and fixed version; upgrade/rebuild rather than silently disabling the gate.                                          |

API logs contain request IDs, route templates, status and duration, not tokens or request bodies. Container logs flow to `/aws/containerinsights/<cluster>/application`; control-plane logs are under `/aws/eks/<cluster>/cluster`. The CloudWatch dashboard and RDS/API alarms are defined in Terraform. Notification targets must be configured and tested separately.

## Roll back application images

```bash
kubectl rollout history deployment/api -n parcelflow
kubectl rollout undo deployment/api -n parcelflow
kubectl rollout undo deployment/web -n parcelflow
kubectl rollout status deployment/api -n parcelflow --timeout=300s
kubectl rollout status deployment/web -n parcelflow --timeout=300s
```

This changes pod images, **not the database schema**. Retain image digests and ensure the previous application is compatible with the current schema. Prefer additive expand/contract migrations. Never edit an applied migration to make its checksum pass. Create a corrective forward migration.

## Database recovery drill

1. Record the source database identifier, recovery point and intended recovery objective.
2. Restore an RDS snapshot or point-in-time copy to a **new private instance** with the same TLS parameter settings.
3. Attach a restricted security group and validate connectivity from a test workload.
4. Check schema migrations, shipment counts and representative event histories.
5. Run the smoke test against an isolated copy of the application using the restored database.
6. Record measured recovery time and data loss. No RTO/RPO is promised by this repository.
7. Review before switching the live endpoint, and delete only the disposable drill resources when finished.

Automatic backups are configured for seven days. Having backups configured is not proof they can be restored successfully.

## Rotate secrets

The RDS master password is managed by RDS/Secrets Manager. Application and operator secrets are generated by the bootstrap job; automatic rotation for them is not configured. For the application DB password, coordinate a Secrets Manager value update with `bootstrap-aws.js` so the PostgreSQL role matches, then roll the API and verify connections. Existing sessions may continue while new connections read the current secret. Schedule this as a controlled maintenance operation.

After changing the operator token, roll the API deployment: it reads that token at startup. Verify the new token works and the old one fails. Do not log either value.

## Costs and teardown

Check EKS control-plane hours, EC2 worker nodes, NAT Gateway hours/data, ALB hours/LCUs, RDS, snapshots, ECR and CloudWatch ingestion/retention. The sample reduces some costs with one NAT Gateway and Single-AZ RDS, at the expense of availability. Set AWS Budgets and alerts appropriate to your account.

Before teardown, decide what data and evidence to retain. Delete the application Ingress and wait for the controller to remove its ALB before deleting the cluster. RDS has deletion protection; a reviewed configuration change is necessary before it can be destroyed. It requires a final snapshot, whose name must not collide with an existing snapshot. ECR repositories are not force-deleted; remove selected images explicitly if you intend to delete them. The Terraform state bucket has `prevent_destroy` and is retained. Secrets have a recovery window. Retained snapshots, log groups and bucket objects may continue to incur charges.

Always inspect a destroy plan and the resource identifiers. There is deliberately no unattended `destroy` workflow.
